# Simple AI Tracker — обязательная инструкция для ИИ-агента

> **Как использовать:** скопируй весь раздел «ПРАВИЛА» (от строки `## Правила работы с тасктрекером`)
> в инструкцию проекта-потребителя (`AGENTS.md`, `CLAUDE.md`, `.cursor/rules` и т.п.).
> Агент, увидев этот блок, обязан работать с трекером **только через MCP**.

---

## Правила работы с тасктрекером (Simple AI Tracker через MCP)

### 0. Контракт доступа — жёсткие ограничения

Работа с задачами ведётся **исключительно** через MCP-инструменты `tracker_*`.

**КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО:**

- вызывать `grep`, `rg`, `find`, `dir`, `ls`, `cat`, `Get-Content`, `Select-String`, `codegraph` и любой другой поиск/чтение по данным трекера;
- открывать, читать, редактировать файлы задач (`tasks/*.json`, `tasks.json`, `tags.json`, `*.db`, `data/tracker.db`, WAL/SHM-файлы);
- обращаться к REST API трекера (`/api/tasks`, `/api/tags`) или писать SQL напрямую;
- искать описание задачи, комментарии, план или ответы пользователя где-либо, кроме `tracker_get_task`;
- угадывать ID задач, придумывать статусы или план «по памяти».

**Если MCP-инструменты `tracker_*` недоступны — останови работу и сообщи пользователю:**
«MCP-сервер Simple AI Tracker недоступен, работа с задачами запрещена без него». Никаких обходных путей
(чтение файлов, REST, SQL) в этом случае не применять.

**Почему так:** карточка и её журнал — единственный источник правды. Файловый поиск и grep дают
устаревший или частичный контекст, ломают кодировку и тратят контекст LLM впустую.

### 1. Обязательный порядок работы с задачей

#### Шаг 1. Пользователь даёт номер задачи
Пользователь называет ID (`SAT-12`) или просит «взять следующую». Второй случай —
`tracker_get_next_task` (вернёт карточку, взятую в работу).

#### Шаг 2. Собрать контекст (обязательный первый вызов)
Вызови `tracker_get_task({ id })`. Он возвращает **контекст-пак**:

- описание, тип, статус, теги, флаг ручного тестирования;
- `relations` — родительская фича, подзадачи, все связи (`blocks`/`blocked_by`/`related`/`duplicates`) с их статусами;
- `plan` — текущий план (markdown целиком) и `planHistory` — все прошлые версии;
- `questions.open` — вопросы без ответа, `questions.answered` — история ответов;
- `decisionLog` — хронология решений: уточнения, версии планов, смены статусов;
- `comments` — история комментариев;
- `workflow.guidance` и `nextActions` — что делать дальше по регламенту.

Никогда не начинай анализ без этого вызова. Если задача связана с другими — прочитай и их
(`tracker_get_task` по каждому связанному ID), чтобы не сломать чужое решение.

#### Шаг 3. Исследование
Изучи код, документацию и скилы проекта (это обычные файлы проекта — читай их как обычно).
Переведи карточку в `planning`: `tracker_set_status({ id, status: "planning", comment: "..." })`.
Всё, что выяснил по ходу, фиксируй комментариями: `tracker_add_comment`.

#### Шаг 4. Вопросы и/или план
Два допустимых исхода исследования:

1. **Нужны ответы пользователя** → `tracker_ask_questions({ id, questions: [...] })`.
   Карточка автоматически уходит в статус `questions` и ждёт ответа. Не продолжай работу.
2. **Решение понятно** → подготовь план в markdown и приложи его:
   `tracker_attach_plan({ id, planContent: "# План…", fileName: "plan-SAT-12.md", summary: "..." })`.
   - План обязателен: в нём цель, шаги, затронутые файлы/модули, план тестирования, риски, критерии приёмки.
   - Если одновременно есть вопросы — передай их в том же вызове (`questions: [...]`): тогда карточка
     останется в `questions`, а план уже будет вложен.
   - План без вопросов переводит карточку в `ready`.
   - `planPath` используй, только если план лежит файлом в проекте (например `docs/plans/SAT-12.md`).

**Если задач в работе несколько:** не останавливайся на первой. Для каждой доводи исследование до
конкретного результата — либо план в карточке, либо все необходимые вопросы. Пользователя уведомляй
одним сообщением со списком карточек, где появились вопросы или готовые планы.

#### Шаг 5. Ответы пользователя
Пользователь отвечает либо **в карточке трекера** (UI), либо **в чате с агентом**.

- Ответил в UI — ответ уже в карточке, статус сменился автоматически (`ready` или `planning`).
  Перечитай задачу: `tracker_get_task`.
- Ответил в чате — **обязан** записать ответы в карточку:
  `tracker_answer_questions({ id, answers: [{ questionId, answer }] })`.
  Ответы, оставшиеся только в чате, считаются потерянными.
- Если после ответов появились новые вводные — оформи их как уточнение (раздел 2) и приложи новую версию плана.
- Перед реализацией убедись, что статус `ready` (если нет — переведи и зафиксируй комментарий).

#### Шаг 6. Реализация строго по плану
`tracker_set_status({ id, status: "in_progress", comment: "..." })`, затем реализуй **по пунктам плана**,
не расширяя скоуп самовольно. Каждый существенный шаг — короткий комментарий в карточку
(`tracker_add_comment`), чтобы работа была воспроизводима.

Если по ходу возник вопрос к пользователю:
`tracker_ask_questions({ id, questions: [...], phase: "implementation" })` — карточка уходит в `questions`,
работа останавливается до ответа. Вопросы задаются **только в карточке**, не в чате.

#### Шаг 7. Тесты
`tracker_set_status({ id, status: "testing", comment: "..." })`. Затем:

- напиши автотесты на изменённое поведение и прогони их;
- проверь критерии приёмки из плана;
- приложи отчёт: `tracker_add_attachment({ id, name: "test-report.md", content: "...", kind: "report" })`
  (что запускал, результат, что не покрыто).

Если тесты красные — вернись в `in_progress` и починить причину, не подгоняя тесты под код.

#### Шаг 8. Готово к проверке пользователем
Тесты зелёные → `tracker_set_status({ id, status: "review", comment: "Тесты: … Что проверить руками: …" })`.

- В карточке флаг `requiresManualTest` указывает, нужна ли ручная проверка пользователя; при
  необходимости дополняй комментарий чек-листом ручной проверки.
- Сообщи пользователю: карточка готова к проверке/тестированию, с кратким итогом и чек-листом.

#### Шаг 9. Done ставит только пользователь
**Агент НИКОГДА не переводит карточку в `done`** — MCP вернёт ошибку `STATUS_REQUIRES_USER`.
Пользователь сам переносит карточку в `done` после проверки. Если пользователь просит доработку —
верни карточку в `in_progress`/`testing` и продолжи цикл.

### 2. Уточнения пользователя по ходу работы (пересборка решения)

Пользователь может уточнить что-то в чате, пока агент уже работает. Это не «мелкая правка на словах»,
а изменение контекста задачи, поэтому:

1. **Зафиксируй уточнение в карточке НЕМЕДЛЕННО:**
   `tracker_record_clarification({ id, clarification, reason, impact, planChanged, questions })`
   - `clarification` — что именно уточнил пользователь (его формулировка, без искажений);
   - `reason` — зачем и почему (мотивация, контекст);
   - `impact` — как это меняет прежнее решение;
   - `planChanged: true` — если предыдущий план больше не актуален;
   - `questions` — если без ответа двигаться нельзя (карточка уйдёт в `questions`).
   Инструмент добавит блок в описание, комментарий `[CLARIFICATION]` и запись в журнал решений.
2. **Перечитай карточку и план:** `tracker_get_task` → `plan.content` + `decisionLog`.
3. **Перепроверь решение с учётом уточнения**: не противоречит ли оно прежним шагам, связям, критериям.
   При необходимости прочитай связанные задачи и код заново.
4. **Обнови план, если решение изменилось:** приложи новую версию через `tracker_attach_plan`
   (`version` увеличится автоматически, история сохранится). В плане явно укажи, что и почему поменялось
   относительно прошлой версии.
5. **Если появился вопрос — задай его через `tracker_ask_questions`** и остановись.
6. **Только после этого продолжай реализацию.**

Смысл: даже если агент «собьётся», в карточке остаётся полный след — что просили изначально, что
уточнили, почему решение поменялось и какая версия плана действует. Никогда не держи уточнения только
в контексте чата.

### 3. Статусы и кто их ставит

| Статус | Значение | Кто ставит |
|---|---|---|
| `backlog` | задача в очереди | агент/пользователь |
| `planning` | агент исследует и готовит план | агент |
| `questions` | заданы вопросы, ждём ответов пользователя | агент |
| `ready` | план согласован, вопросов нет | агент |
| `in_progress` | реализация строго по плану | агент |
| `testing` | пишутся и прогоняются тесты | агент |
| `review` | тесты зелёные, ждёт проверки пользователя | агент |
| `done` | проверено и закрыто | **только пользователь** |

Недопустимые переходы (например `backlog → review`) отклоняются с ошибкой `INVALID_TRANSITION` —
это защита от «перескока» регламента.

### 4. Карта инструментов

| Инструмент | Назначение |
|---|---|
| `tracker_get_instructions` | вернуть эту инструкцию (если потерял контекст) |
| `tracker_get_task` | контекст-пак карточки: описание, связи, план, вопросы, журнал решений |
| `tracker_list_tasks` | список задач с фильтрами (status/type/tag/parentId/query) |
| `tracker_search_tasks` | полнотекстовый поиск (title/description/comments/tags/id) |
| `tracker_get_next_task` | взять следующую готовую задачу (`ready` → `in_progress`) |
| `tracker_create_task` | создать фичу/задачу/баг (с тегами, связями, флагом ручного теста) |
| `tracker_update_task` | изменить название/описание/тип/теги/флаг ручного теста |
| `tracker_set_status` | сменить статус (с комментарием в историю) |
| `tracker_add_comment` | комментарий в карточку (ход работы, решения, результаты) |
| `tracker_ask_questions` | задать вопросы пользователю → статус `questions` |
| `tracker_answer_questions` | записать в карточку ответы, полученные в чате |
| `tracker_attach_plan` | приложить план (markdown) с автонумерацией версий |
| `tracker_record_clarification` | зафиксировать уточнение пользователя и пересборку решения |
| `tracker_add_attachment` | приложить отчёт/файл (например `test-report.md`) |
| `tracker_link_tasks` / `tracker_unlink_tasks` | связать/развязать карточки |
| `tracker_list_tags` / `tracker_add_tag` | реестр тегов |
| `tracker_verify_task` | компактная проверка целостности карточки (вместо diff/grep) |

### 5. Что и куда писать

- **Описание задачи** — требования и критерии приёмки. Дополнения пользователя идут в блок
  `### Дополнительные требования пользователя (добавлено в процессе):` (это делает `tracker_record_clarification`).
- **План** — отдельное вложение (`kind: "plan"`), не текст комментария.
- **Вопросы** — только `tracker_ask_questions` (структурированные вопросы карточки), не комментарий «вопрос: …».
- **Отчёты о тестах и результатах** — вложение `kind: "report"` + короткий комментарий.
- **Ответы пользователя** — только через UI трекера или `tracker_answer_questions`.

### 6. Антипаттерны (нарушение = отказ в приёмке работы)

- Искать задачи grep-ом, читать `tasks.json`/`*.db`, править JSON задач руками.
- Задавать уточняющие вопросы в чате вместо карточки.
- Начинать реализацию без плана в карточке или «по памяти».
- Молча менять решение после уточнения пользователя, не обновив план и журнал.
- Ставить `done` самостоятельно.
- Расширять скоуп задачи по собственной инициативе.
- Оставлять тесты красными и переводить карточку в `review`.

## Как подключить MCP-сервер (для человека, один раз)

1. Установи зависимости в каталоге `simple-ai-tracker`: `npm install --omit=dev` (для MCP)
   или `npm install` (если нужен ещё веб-интерфейс).
2. Пропиши MCP-сервер в конфигурации агента (пример — `mcp.config.example.json`):

```json
{
  "mcpServers": {
    "simple-ai-tracker": {
      "command": "node",
      "args": ["<абсолютный или относительный путь>/simple-ai-tracker/scripts/mcp-launcher.mjs"]
    }
  }
}
```

Лаунчер сам соберёт сервер при первом запуске, база `data/tracker.db` создастся автоматически.
3. Скопируй раздел «Правила работы с тасктрекером» в `AGENTS.md` проекта-потребителя.
4. Для работы UI запусти HTTP-сервер трекера (`npm start`) → `http://127.0.0.1:4317`.
5. Диагностика установки: `npm run doctor`.

Пошаговая инструкция по переносу в другой проект — [`GETTING-STARTED.md`](GETTING-STARTED.md).
