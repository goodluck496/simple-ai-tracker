## Antigravity: подтверждённый официальный путь

Официальный CLI поддерживает `agy models`, `agy -p ... --model <slug>`, JSON/stream-json результаты, `--json-schema`, продолжение разговора и терминальные статусы. Есть usage в итоговом результате. Для первого этапа достаточно отдельного процесса на роль, а не долговечной общей сессии.

Источники: [headless CLI](https://antigravity.google/docs/cli/headless/), [CLI reference](https://antigravity.google/docs/cli/reference/).

CLI устанавливается отдельно. Официальная документация описывает общий вход между App/CLI/IDE и silent sign-in через системное хранилище; значит, не требуется подменять агентскую систему прямым Gemini API. Фактический вход установленного CLI ещё нужно подтвердить после его появления — наличие открытого desktop-окна само по себе не является handshake трекера.

Источники: [установка](https://antigravity.google/docs/getting-started), [аутентификация](https://antigravity.google/docs/install?tab=cli).

В открытой официальной справке подтверждён `agy models`, но точный машинный формат каталога и флаг `--json` не проверены на локальном бинарнике. Парсер нельзя писать по случайному примеру из стороннего проекта: сначала version/help/models и сохранённая обезличенная fixture. Не считать soft-denied инструмент успешным выполнением задачи только по exit=0.

## DeepSeek Harness: runtime, профиль и каталог

В установленном runtime обнаружены `llm.listProviders()` и `llm.listModels(provider)`. Это методы сервиса Harness, а не доказательство наличия внешней CLI-команды `dsh models`. Установленный headless печатает финальный текст; пакет SDK/ACP в проверенном наборе Desktop не обнаружен. Состояние текущего upstream нельзя автоматически приписывать установленной версии.

В upstream есть официальные headless, SDK JSON-RPC и ACP профили. SDK даёт initialize, prompt, wait, resume, вопросы/approvals и shutdown. В опубликованной таблице SDK методов нет отдельного list-models — нельзя выдумывать `models.list`. Каталог требует подтверждённого bridge к llm-сервису или отдельно поддерживаемой поверхности discovery.

Источники: [CLI](https://github.com/deepseek-ai/deepseek-harness/blob/master/apps/cli/README.md), [SDK protocol](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/sdk/protocol/README.md), [SDK server](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/sdk/server/README.md).

Современный upstream Desktop описывает управляемую команду dsh и общее продуктовое хранилище, но отдельное владение исполняемыми профилями; CLI не должен запускать desktop-профиль. У установленной старой версии другая упаковка. Нужно version-gated обнаружение, без редактирования её web-профиля, чтения ключей или использования её живых сессий как тестовых.

Источник: [Desktop command/runtime ownership](https://github.com/deepseek-ai/deepseek-harness/blob/master/apps/desktop/README.md#bundled-command-runtime).

## План реализации

1. **Диагностика подключения без генерации.** Для каждой системы показывать путь и версию runtime, состояние входа (только через поддерживаемую команду), доступность каталога и конкретную причину отказа. Различать not-installed, not-on-PATH, login-required, unsupported-version и ready. Отсутствие capabilities не заменять фиктивным каталогом. Discovery пути — PATH, явный пользовательский путь, затем документированные каталоги; bundled DSH launcher должен учитывать executable + argv, а не строку shell.
2. **Antigravity adapter.** После наличия официального CLI проверить help/models без модельной задачи. Подключить версионированный парсер каталога к текущему worker model mailbox; добавить структурированный результат, schema, session id, статусы, отмену и нормализованный usage с точными правилами cached/cumulative. Не переписывать глобальные permissions и не включать обход подтверждений.
3. **DeepSeek adapter.** Использовать обнаруженный bundled CLI с совместимым Node либо явно установленный CLI. Выделить собственный automation-профиль вместо изменения живого desktop/web. Для установленного headless показывать capability `profile-bound model` и проверять/явно объяснять эффективную модель; не сохранять ложное обещание, что произвольный model ID применяется. Для новых совместимых версий исследовать SDK/ACP с отдельными сессиями и рабочими папками.
4. **DSH discovery bridge.** Отдельная минимальная композиция/плагин через документированные Harness API получает имена провайдеров/моделей и эффективную модель профиля, не возвращая credentials и не делая prompt-запросов. Проверить совместимость с установленной 0.1.1-rc.2; если нужной поддерживаемой поверхности нет, показать причину и оставить явный профильный режим. Обновление Desktop/установка другого runtime — отдельное явное действие, без автоматической смены пользовательской версии.
5. **UI и передача контекста.** Общие действия Проверить подключение / Обновить модели / Выбрать модель / Проверить запуск; отображать реальный путь runtime и capabilities. Сохранить текущие PrimeNG-контролы, индивидуальную роль/модель и существующие настройки Codex. Полный контекст каждой системы не передавать другим системам; сохранять текущие ограниченные handoff и внешние журналы.
6. **Приёмка.** Read-only probe + fixture tests для всех ответов/версий; без установленного CLI честно not-installed. Затем один ограниченный реальный запуск на каждую систему в отдельном временном репозитории: изменение файла, JSON verdict, фактическая модель, отмена, usage либо unknown и сохранение результата. Ни одной пользовательской задачи в тестовой очереди. Общие tests/typecheck/build/browser и review после подтверждённого поведения.

## Что пока не доказано

- Реальная авторизация и выполнение в Antigravity CLI: локального бинарника не найдено.
- Доступность SDK/ACP и внешнего каталога у установленного старого DSH: этих компонентов в проверенном наборе нет; внутренний llm-сервис найден, безопасная внешняя композиция не проверена.
- Совместное использование входа desktop/headless у этой конкретной установленной версии DSH: проверять через runtime, не извлечением секретов.
- Управление существующими открытыми desktop-разговорами не реализовано и не требуется для отдельных задач tracker/worktree.

Исследование не является отчётом об успешно установленной интеграции. Следующий функциональный этап — probe/capabilities и Antigravity discovery; DSH требует отдельного versioned bridge, а не ещё одного поля в настройках.
