# SAT-1: завершение проверки рабочих пространств

## Граница работы
Работать только с актуальной основной реализацией отдельного репозитория E:/work/developing/pet-projects/simple-ai-tracker (baseline db4d29d). Цель — подтвердить независимые списки задач, отдельные SQLite-базы и резервирование каждой базы. Не сливать целиком archive/sat-1-agent-result: это другая реализация. Не запускать прежний конвейер.

## Подтверждено аудитом
- WorkspaceManager.within закрепляет контейнер через AsyncLocalStorage.
- Два текущих теста workspace-manager.spec.ts прошли: A/B/A, одинаковые ID в разных БД, конкурентный scoped-доступ, HTTP и MCP.
- UI хранит выбор в sessionStorage и перезагружает страницу; /activate возвращает подтверждение выбора, не меняя глобальную БД. Это согласованная модель независимых вкладок, а не само по себе ошибка.
- В api-entry.ts один BackupScheduler получает app.backupService при старте; далее он резервирует только эту БД. Все остальные пространства не обходятся. Это подтверждённый блокер приёмки.
- Удаление открытого пространства сейчас отклоняется с 409; не подменять этот контракт реализацией из архивной ветки и не расширять задачу удалением файлов.

## Шаги завершения
1. Добавить координатор автоматических бэкапов всех пространств. На старте и каждом цикле получать актуальный список, входить в within(name) и выполнять существующую политику интервала/суточного лимита/ротации для соответствующей BackupService. Один управляемый таймер координатора, stop при shutdown; изолировать ошибку одной БД от остальных.
2. Проверить пространство, созданное после запуска API или другим MCP-процессом: оно должно попадать в следующий цикл. Реестр перечитывать; удалённые записи не обходить. Не менять глобальный выбор пользователя во время резервирования.
3. Добавить временные fixture-тесты: две БД с разными задачами, ручные и автоматические снимки каждой, независимая ротация/суточные лимиты; открыть/восстановить обе копии в отдельные временные контейнеры и проверить данные. Рабочие базы не читать вне tracker MCP.
4. Дополнить проверки legacy default с данными, повторного открытия менеджера, ошибок имён/дубликатов и конкурентных запросов разных пространств. Проверить список/скачивание бэкапа в scoped HTTP/MCP-контексте.
5. После сборки выполнить существующий scripts/verify-workspaces.ts на изолированных данных: создание, A/B/A, независимые вкладки, reload. Не выдавать отсутствие локального dist за дефект пространства.
6. Один полный npm test, npm run typecheck и npm run build; сохранить компактный отчёт, коммит только относящихся к задаче файлов. Затем testing → review; done ставит пользователь.

server/src/bootstrap/api-entry.ts; новый координатор в server/src/services/ и тест рядом; server/src/core/workspace-manager.spec.ts; scoped API/backup регрессии; существующий browser smoke.

## Приёмка и ограничения
Каждое пространство имеет собственные задачи, SQLite и проверяемые ручные/автоматические бэкапы. Переключение/перезапуск/параллельные запросы не смешивают данные. Фактически выполненные проверки указаны отдельно от непроверенных требований. Архивные тесты и отчёты не доказывают готовность текущей ветки.
Отдельная SAT-2 отвечает за действие «Убрать из очереди»; оно не входит в SAT-1.
