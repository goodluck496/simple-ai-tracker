# Роутер задач и проверяемая приёмка (SAT-50)

## Настройка

В «Команда агентов → Команда и этапы» добавьте роль «Роутер» первым этапом.
Для изменения кода оставьте разработчика, тестировщика и ревьюера; аналитик нужен,
если требования требуют исследования. Роутер работает только на чтение и не меняет
глобальные настройки, лимиты или набор этапов.

Создайте альтернативные профили с нужными моделями и выберите их в «Разрешённые
профили моделей». Роутер может заменить профиль будущего этапа только профилем той
же роли из этого списка. Пустой список сохраняет все выбранные модели. Новые
профили и провайдеры не создаются автоматически. Модель самого роутера выбирает
пользователь. Реальное качество конкретной модели требует проверки на задачах.

Решение содержит сложность, риск, неопределённость, причины, цель, границы и
критерии AC-*. Высокая неопределённость требует аналитика или ответов пользователя.
Исходная карточка сохраняется. Пакет критериев передаётся всем следующим ролям,
а эффективная модель записывается в usageAttempts. Решение сохраняется в самом
запуске, а не в глобальной конфигурации. После изменения описания остановленный
запуск при обычном продолжении возвращается к роутеру в той же worktree. Коммиты,
история и потраченный бюджет сохраняются; старые критерии, приёмка и контекст
этапа сбрасываются. Если есть аналитик, он пересматривает план следующим этапом.
Декомпозированные исполнения требуют отдельной проверки дочерних планов.

## Смена агентов и анализ сбоев

В деталях очереди нажмите «Изменить агентов запуска». Выберите текущий или будущий
этап, сохранённый профиль той же роли и ID модели. Во время работы можно менять
будущие этапы; для текущего сначала нажмите «Остановить». Изменение не создаёт
нового запуска и не изменяет настройки проекта. Уже выполненные этапы остаются
в истории с фактическими моделями. После изменения текущего остановленного этапа
продолжение запускается отдельно. Ручной выбор имеет приоритет перед решением
роутера. Изменение состава/порядка этапов работающего запуска не поддерживается.

Анализ показывает подтверждённую причину, гипотезу или явное отсутствие диагноза,
свидетельства и шаги восстановления. Изменение требований и лимиты провайдера
распознаются без модельного вызова и не отправляются на ремонт кода. Для неизвестной
причины показываются шаги исследования; готовый patch не выдумывается. Кнопка
применения явно называет действие. Пустые diff и список файлов скрыты.
Отклонённая промежуточная JSON-запись не означает отказ итогового результата:
следующая корректная запись может быть опубликована. Требования к формату и лимиту
списков передаются в stage-context.json и инструкциях агента.

## Проверки

Разработчик пишет код и тесты; тестировщик и ревьюер работают только на чтение.
Тестировщик возвращает в строковом поле plan JSON следующего вида:

```json
{"results":[{"id":"AC-1","status":"passed","evidence":"persistence.spec.ts: после перезагрузки значение сохранено"}]}
```

Каждый критерий должен присутствовать ровно один раз. Допустимые статусы: passed,
failed, manual. Manual допускается только для критерия с методом manual. Такой
критерий остаётся ручной проверкой пользователя и не считается автоматически
пройденным. Для browser необходимы реальные действия и проверки результата,
а также существующий screenshot в поле screenshots результата этапа. Worker
запускает настроенные команды независимо от отчёта модели. Сам отчёт сценариев
остаётся свидетельством агента, а не математическим доказательством покрытия.

Результаты привязаны к SHA: новый коммит или этап записи инвалидирует старую
приёмку. Завершение запуска с кодом требует отчёта для текущего SHA. События
routing содержат оценки, число критериев и замен; acceptance — SHA и количество
passed/failed/manual. Время и токены доступны в существующих usageAttempts.

## Браузер

В настройках проекта включите «Worker запускает тестовое приложение» и задайте
команду, аргументы как JSON-массив и путь готовности. Например команда npm,
аргументы `["run","dev","--","--port","{port}"]`, путь `/`.
Worker запускает сервер из worktree, подставляет выделенный PORT, ожидает HTTP
2xx/3xx до 60 секунд и завершает процесс после этапа или при ошибке. Готовность
публикует startupMs. База, фикстуры и тестовая авторизация остаются настройкой проекта.

Подключите Playwright MCP через docs/agent-environment.json с нужными инструментами
и roles ["tester"]. Управляемые проектные MCP поддерживают Codex и Model API.
Для других CLI используются возможности их harness. Для обычного CI подходят
настроенные команды Playwright. Для просмотра изображений API-профиль должен
иметь supportsImages=true; MCP-изображения PNG/JPEG/WebP передаются в контекст
модели, до четырёх ограниченных по размеру изображений за шаг. Для text-only
подключения явно сообщается, что изображение не просмотрено.

## Локальная проверка

`npm run typecheck`, `npm run build:server`, `npm run build:web`.
Новые тесты: task-routing.spec.ts, browser-session.spec.ts, project-mcp-tools.spec.ts.
`node --import tsx scripts/verify-task-routing.ts` проверяет сохранение настроек
в изолированном тестовом приложении без вызова моделей, desktop/mobile, ошибки
страницы и доступность содержимого. Артефакты: .sat/screenshots/routing-*.png,
.sat/routing-ui-trace.zip, .sat/routing-ui-metrics.json.

Чтобы применить исходники в установленном приложении, необходим штатный выпуск
API/UI и перезапуск worker. Проверка реальных CLI, MCP и аккаунтов выполняется
после настройки на соответствующем компьютере; fixture-тесты её не заменяют.
