# Команда агентов и worker

Правила загрузки инструкций, выбранных скилов и проверки проектных MCP:
[окружение агента в worktree](project-agent-environment.md).

Откройте кнопку с молнией «Команда агентов» в шапке трекера. Настройки и запуски
относятся к выбранному пространству. Секретные ключи остаются на машине worker:
в подключении указывается только имя переменной окружения.

## Настройка

Панель разделена на шаги: подключение компьютера → проект и проверки → подключения
моделей → команда → порядок этапов → запуск. Имя Docker-контейнера скрыто в
расширенных настройках подключения. После системного выбора папки ветки и scripts
читаются автоматически. При ручном вводе пути нажмите Enter или выйдите из поля;
кнопка чтения проекта позволяет повторить запрос.

Стандартная команда создаёт четыре разных профиля с уникальными ID и базовыми
инструкциями: аналитик, разработчик, тестировщик, ревьюер. Инструкции объясняют,
что делать, что возвращать и какие изменения разрешены. Для дизайнера и визуального
валидатора тоже есть свой текст. Его можно редактировать; кнопка «Вставить базовую
инструкцию» заменяет текст базовым для выбранной роли. Смена роли заменяет только
прежний базовый или пустой текст, а пользовательскую инструкцию сохраняет.

Если старые настройки содержат совпадающие timestamp-ID, форма исправляет их
только в черновике и показывает предупреждение. Проверьте этапы и сохраните:
модели, подключения и свои инструкции сохраняются. История запущенных задач не
переписывается. Независимость роли означает отдельный запуск с её инструкциями;
для разных взглядов можно выбрать разные модели и исполнители.

1. Запустите worker для выбранного пространства (команда ниже). В панели появится
   «Worker: подключён». Выберите папку через браузер каталогов worker или введите
   абсолютный путь и нажмите «Прочитать проект и ветки». Windows-пути читает worker,
   а не Linux-контейнер трекера. Можно войти в подпапки и подняться на уровень выше;
   для другого диска введите путь вручную. Показываются локальные ветки Git.
2. Выберите базовую ветку. Для новой введите имя и нажмите «Создать ветку»:
   она создаётся от выбранной без checkout. Не создавайте её повторно; существующая
   ветка не перезаписывается. После создания она становится выбранной базой.
3. Накликайте подготовку (один раз перед этапами), например `npm ci`, и проверки
   (после изменений). После чтения проекта теги проверок соответствуют его scripts
   из package.json. Нажатие тега только выбирает команду, не запускает её.
   Свои программы и JSON-аргументы доступны в «Расширенной настройке».
4. Создайте подключения кнопками «Codex CLI», «DeepSeek API», «DeepSeek Harness»,
   «Ollama» или вручную. Codex использует native и вход установленного CLI.
   DeepSeek API использует openai-compatible, адрес https://api.deepseek.com,
   имя переменной DEEPSEEK_API_KEY (сам ключ в окружении worker). DeepSeek Harness
   использует native и отдельный профиль установленного dsh.
   Создайте агентов или стандартную команду из четырёх ролей. У каждого выбираются роль, исполнитель,
   подключение, модель и инструкции. Разные роли могут использовать разные модели.
5. Расставьте этапы стрелками. Аналитик при необходимости идёт первым; разработка
   и дизайн — перед тестами; ревью и визуальная проверка — после тестов. Можно
   добавить несколько разработчиков, тестировщиков, ревьюеров и визуальных проверок.
6. Выберите задачу через p-select с поиском. В опции указаны статус и готовность.
   DoR по полям трекера означает ready + существующий план + отсутствие открытых
   вопросов; качество содержания плана отдельно оценивает команда. Без DoR можно
   войти через анализ первым этапом. Вопросы, активный запуск и неподходящий статус
   блокируют новую очередь с объяснением в списке.
7. Нажмите «Запустить» (либо «Поставить в очередь», когда worker отключён).
   Текущие настройки формы валидируются и атомарно сохраняются вместе с immutable
   snapshot запуска. Предварительное отдельное сохранение не требуется. При ошибке
   запуск не создаётся и сохранённые настройки не меняются. Сообщение об ошибке,
   созданный run ID и текущий статус видны прямо под кнопкой; polling их не стирает.
   Ошибка обновления журнала не отменяет уже успешно созданный запуск. Offline
   очередь ожидает подключения worker — это явно показано в результате.

Скриншоты необязательны. Оставьте блок пустым для обычных задач. Для визуального
валидатора проверки должны создать PNG/JPEG/WebP в рабочей папке проекта;
укажите относительные пути этих файлов и подключение с поддержкой изображений.
Поле путей не загружает файлы с компьютера и не переносит автоматически картинки
из карточки. Например, Playwright может сохранять screenshot в test-results/page.png.

Задача без плана требует аналитика. Неразрешённые вопросы блокируют запуск.
Настройки копируются в запуск: последующее редактирование команды не меняет
уже выполняющуюся задачу.

## Подключения и исполнители

| Исполнитель | Подключение | Модель |
|---|---|---|
| `codex` | `native`, вход Codex CLI на worker | ID модели Codex |
| `claude-code` | `native`, вход Claude Code на worker | ID/alias Claude |
| `opencode` | `native`, провайдеры OpenCode на worker | `provider/model` |
| `antigravity` | `native`, установленный `agy` | slug модели Antigravity |
| `deepseek-harness` | `native`, установленный `dsh` | выбирается в headless-профиле DSH |
| `model-api` | `ollama` или `openai-compatible` | ID модели API |
| `custom` | `native`, собственный CLI/SDK bridge | передаётся через `{model}` |

Для DeepSeek Harness задайте имя собственного профиля с headless bundle и
нужной моделью. Поле модели в трекере должно описывать модель этого профиля:
адаптер не переписывает внутреннюю конфигурацию DSH.

Для Ollama адрес обычно `http://localhost:11434`: HTTP-запрос выполняет worker,
поэтому адрес относится к его машине. Совместимый API задаётся до
`/chat/completions`, например `https://api.deepseek.com` или адрес с `/v1`.
Выбранная модель должна поддерживать tool calling для работы с файлами.
Чистому визуальному валидатору достаточно поддержки изображений.
Reasoning effort оставьте пустым для настроек модели либо выберите поддерживаемое
ею значение. Доступный размер контекста локальной модели задаётся в Ollama;
пустой/оборванный ответ не считается успешным результатом.

Нативные CLI используют собственные настройки провайдеров, MCP и разрешений.
Отсутствующий CLI, ошибка входа, отказ инструмента или неверный JSON-результат
не считаются успешным выполнением. Дополнительные возможности можно подключить
через `custom`: executable + массив argv с `{promptFile}`, `{model}`, `{cwd}`,
`{role}`, `{provider}`. Bridge читает UTF-8 файл задания и печатает итоговый JSON:

```json
{"verdict":"pass","summary":"Что сделано и проверено"}
```

Другие verdict: `changes_requested` и `questions`. Для вопросов нужен массив
`questions`; аналитик при `pass` возвращает markdown в поле `plan`.

## Запуск worker с Docker-трекером

В первом шаге панели нажмите **«Скопировать команду запуска»**.
Вставьте всю команду в PowerShell и нажмите Enter. Текущая папка терминала любая:
клон tracker в целевом проекте не нужен. Команда скопирует один готовый worker
из Docker в LocalAppData/SimpleAiTracker/workers и запустит его через Node.js.
Зависимости JS включены в этот файл. На компьютере нужны Node.js 22+ и Docker CLI.

Команда подключения не использует путь проекта: она запускает общий worker
пространства из папки helper. Даже неверный путь в форме не мешает подключению.
Нажмите **«Подключить и выбрать папку»**, если worker ещё не работает: команда
скопируется (либо появится для Ctrl+C), а после её запуска выбор откроется
автоматически. Ожидание можно отменить. Если worker уже подключён, кнопка
**«Выбрать папку»** сразу открывает диалог.
Обновлённый Windows worker откроет стандартный системный диалог в своей сессии.
На выбор есть минута; отмена сохраняет прежний путь. Для других ОС и старых worker
остаётся «Обзор каталогов worker». Если worker запущен как неинтерактивная служба,
используйте обзор каталогов вместо системного окна.

В «Расширенных настройках подключения» можно поменять имя Docker-контейнера. Пространство
подставляется автоматически с экранированием; путь проекта в команду не включается. Если Clipboard API
недоступен, команда показывается и выделяется для Ctrl+C. Оставьте PowerShell
открытым; Ctrl+C останавливает worker. После обновления Docker остановите старый
worker и выполните заново скопированную команду.

Для разработки из исходников, из корня отдельного репозитория `simple-ai-tracker`:

```powershell
npm run worker -- --workspace simple-ai-tracker
```

Команда собирает host worker и подключается к MCP через `docker exec -i`.
`worker:docker` сохранён как синоним. Для другого пространства замените `simple-ai-tracker` его ID.
`SAT_CONTAINER` переопределяет имя контейнера. Для проверки очереди один раз:

```powershell
npm run worker -- --workspace simple-ai-tracker --once
```

Для трекера полностью без Docker: `npm run build:server`, затем `npm run worker:local`.
Не запускайте `worker:local` на Windows одновременно с Docker API над тем же SQLite-стором:
он создаёт Windows MCP, тогда как контейнер использует Linux SQLite/WAL. Выбирайте один runtime
для доступа к данным. Обычная команда `worker` теперь использует Docker, чтобы случайный запуск
не открывал контейнерную базу из Windows.
`SAT_WORKSPACE` задаёт пространство. `SAT_MCP_COMMAND` и `SAT_MCP_ARGS`
(JSON-массив) позволяют подключить другой stdio MCP launcher.
Процесс можно зарегистрировать в системном диспетчере служб; отдельный cron
не нужен: worker проверяет явно поставленные в очередь запуски каждые 5 секунд.

## Выполнение и проверка

Worker создаёт соседний каталог `.sat-worktrees/<run-id>` и ветку `sat/<run-id>`.
Исходная рабочая папка не используется для редактирования. Worktree — изоляция
изменений Git, а системные разрешения нативного агента задаёт его harness.
У model-api роли разработчика/дизайнера могут писать файлы внутри worktree;
остальные роли получают чтение и настроенные проверки. Лимит — 40 модельных
итераций плюс общий таймаут запуска.

После тестировщика worker сам запускает все настроенные команды, проверяет SHA
и чистоту дерева. Слова модели о зелёных тестах не заменяют эти команды.
Замечания возвращают выполнение к разработчику до лимита доработок. В карточку
прикладываются планы, отчёты тестировщика/ревьюера и ссылки на branch/SHA.

Для визуальной проверки задайте PNG/JPEG/WebP пути относительно проекта и
команду проверки, которая генерирует эти изображения. Включите поддержку
изображений у подключения. API-валидатор получает изображения непосредственно;
нативному агенту передаются пути для его инструментов. Отсутствующее изображение
останавливает запуск.

По умолчанию `manual` оставляет готовую ветку на ручное слияние. Политика `local`
делает только `git merge --ff-only` в чистую основную ветку на хосте worker.
Push, PR и внешние CI-проверки автоматически не создаются. После слияния карточка
остаётся в `review`: `done` ставит пользователь.

## Остановка и продолжение

Остановка из панели отзывает lease. Worker замечает её на heartbeat (до 15 секунд)
и прекращает дочерние процессы. Lease без heartbeat истекает через 90 секунд:
запуск становится `interrupted`, а не запускается повторно автоматически.
После проверки оставшихся процессов нажмите «Продолжить». Сохраняются этап,
ветка, настройки, SHA и отчёты; новая модельная сессия получает этот контекст.
Перенос внутренней сессии одного harness в другой не выполняется.

Ответьте на вопросы в карточке перед продолжением. После вопросов на этапе
тестов/ревью worker возвращается к разработчику и повторяет проверки. Если все
этапы завершены, но слияние не удалось, выполните слияние вручную.

## Проверки интеграций

### Декомпозиция фич и бюджет

Журнал содержит короткие результаты действий и ошибки, без исходников, patches,
MCP payload и рассуждений. Файлы остаются в репозитории. Исторические JSON-события
в читаемой консоли тоже отображаются без дампов кода; сырой старый журнал доступен
только по явному запросу. Скрытие журналов само по себе не доказывает экономию
provider tokens. Codex получает ограничение tool output 800 токенов; роли читают
нужные фрагменты и применяют patches. API tools поддерживают read_file по 40 строк,
edit_file для точного изменения и write_file только для создания нового файла.

На хосте worker обязателен CodeGraph (`codegraph` в PATH), кроме Node.js, Docker и
Git. Worker создаёт отдельный индекс каждого worktree и синхронизирует его перед
ролью; общий индекс репозитория не подключается. Codex получает MCP только с
codegraph_explore, привязанным к worktree. На Windows npm-обёртка обходится прямым
запуском установленного платформенного runtime. Graph watcher выключен: актуальность
между ролями обеспечивает sync. Остальные CLI используют CodeGraph CLI, API-агенты —
explore_code. Запросы — один точный символ, maxFiles=1, без повторного чтения уже
полученного исходника. Ошибка подготовки останавливает worker до платного вызова.

Аналитик может вернуть `decomposition` из 2–12 задач с полями `key`, `title`,
`description`, `plan`, `dependsOn`. Атомарной задаче достаточно пустого массива.
Вопросы пользователя имеют приоритет: до ответа не создаются дочерние задания.
Понятное разбиение автоматически создаёт карточки с планами и направляет их
разработчикам. Первая версия исполняет DAG последовательно, без рекурсивных аналитиков.

Дети работают в отдельных ветках/worktree, проходят developer/reviewer и squash
в частную ветку фичи. Полные configured checks и финальное ревью проверяют уже
собранную фичу; затем выполняется один squash в основную ветку. Дочерние карточки
переходят в review, done остаётся действием пользователя. Очередь показывает их
ссылки, состояние доставки и SHA. Изменение родительского плана требует пересмотра
разбиения; старые дочерние планы автоматически не используются.

Все дети входят в исходный запуск и расходуют общий бюджет. Аналитик выбирает
разбиение, сервер автоматически рассчитывает число вызовов: плановые этапы плюс
конечный резерв по оставшимся общим maxRevisions и maxResolverCalls. Например,
три ребёнка требуют 9 плановых вызовов; с одним общим циклом исправления (до 3
вызовов) и одним resolver общий предел равен 13. Резерв не запускается без причины.
Дочерних аналитиков нет, DAG ограничен 12 детьми, общий потолок — 100 вызовов.
Число исправлений не обнуляется на каждом ребёнке. Для атомарных задач остаётся
обычный maxAgentCalls; для фич расчёт виден в очереди и вручную не редактируется.

Лимиты входных токенов и времени автоматически не повышаются. Пользователь может
изменить их в деталях остановленного запуска; потраченный бюджет сохраняется.
Старые остановки по числу вызовов продолжаются через «Продолжить с места остановки»:
аналитик восстанавливается из checkpoint, расчёт выполняется без повторного вызова
модели. Накопленный вход включает cached input и не является размером окна или
денежной ценой; native CLI может сообщать usage с задержкой.

Успех `npm test` печатается одной строкой; ошибки содержат trace. Роли получают
work order и краткий handoff вместо сырых логов. `maxStageToolCalls` ограничивает
наблюдаемые обращения native-агента к инструментам (по умолчанию 24), а не число
провайдерских HTTP-запросов. Оба ограничения не являются гарантией финансового потолка.

- `npx tsx scripts/verify-automation.ts` — настройки, очередь/остановка, три размера экрана.
- `npx tsx scripts/smoke-native.ts codex <model>` — реальный неинтерактивный CLI.
- `npx tsx scripts/smoke-model.ts <ollama-model>` — реальная модель и чтение файла.
- `npx tsx scripts/smoke-vision.ts <vision-model>` — реальное распознавание изображения.
- `npx tsx scripts/smoke-pipeline.ts <model> [runner=model-api]` — полный цикл на временном Git-проекте; например с `codex` или локальным API.

Smoke-команды используют временные данные и не ставят в очередь задачи пользователя.
Контрактные тесты остальных CLI проверяют построение команд и разбор ответов;
они не заменяют проверку установленного harness и его аккаунта.

Протоколы: [Codex exec](https://learn.chatgpt.com/docs/non-interactive-mode),
[Claude Code](https://code.claude.com/docs/en/headless),
[OpenCode](https://dev.opencode.ai/docs/cli/),
[DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/cli-help.md),
[Antigravity](https://www.antigravity.google/docs/cli/headless/).
