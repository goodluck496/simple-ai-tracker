# SAT-3: параллельные задачи и squash-слияние

Каждая задача выполняется в отдельной ветке и Git worktree рядом с исходным репозиторием. `maxParallelRuns` ограничивает число одновременно исполняемых задач; общий координатор Git-репозитория учитывает разные workspace и процессы worker. Изменение числа исполнителей применяется после перезапуска worker. Режим `--once` обрабатывает одну задачу.

При `mergePolicy: local` worker создаёт отдельного кандидата squash, проверяет именно этот коммит и последовательно переносит его в `baseBranch` (например, `master`). Исходный checkout должен находиться на целевой ветке и быть чистым. Ветки и worktree сохраняются для диагностики. Удалённый push и создание MR не выполняются.

## Зависимости

`dependencyMode: isolated` — значение по умолчанию. Режим `linked` создаёт отдельный управляемый npm-кеш по manifest/lock, Node, npm, платформе и настройкам установки. Пользовательский `node_modules` не изменяется. Пакеты подключаются junction/symlink, а `.bin`, `.cache` и временные каталоги остаются локальными. Кеш защищён от записи; при изменении manifest зависимости отсоединяются и устанавливаются отдельно.

Неподдерживаемые проекты (включая workspace/link-зависимости и специальные сценарии установки) используют изолированную установку. Под POSIX root режим также изолированный. Инструменты, записывающие данные внутрь собственных пакетов, могут быть несовместимы с readonly-кешем: для них выбирайте `isolated`. Совместимость всех сторонних npm-пакетов не гарантируется.

## Конфликты и восстановление

`maxMergeAttempts` ограничивает пересборку кандидата при движении целевой ветки. `resolveConflicts`, `maxResolverCalls`, `resolverTimeoutMinutes`, `maxResolverToolCalls` ограничивают дополнительного агента-разработчика. Он получает ограниченный контекст конфликтов; изменение посторонних файлов, HEAD или ветки отклоняется. После разрешения выполняются проверки кандидата. Неоднозначный конфликт или провал проверки оставляет задачу в `merge_blocked`, сохраняя основную ветку.

После остановки проверьте оставшиеся процессы, затем используйте продолжение: завершённые роли повторно не исполняются. Если общий бюджет исчерпан, допускается только подтверждение уже опубликованного коммита, без новых модельных вызовов. Явный повтор завершённого конвейера запускает только интеграцию сохранённого исходного SHA с новым бюджетом. Изменённый контекст задачи может потребовать такого повтора.

Журнал интеграции хранит SHA и контрольные точки. Повторное подтверждение опубликованного кандидата не создаёт второй squash-коммит. Повреждённая или неоднозначная контрольная точка останавливает исполнение. Во время короткой критической операции публикации остановка откладывается до завершения Git; лимит этой операции — 120 секунд.

Состояния, пути worktree и SHA доступны в очереди. Токены решателя учитываются отдельно. Нативные CLI могут сообщать usage лишь по завершении: лимит токенов не является гарантированным пределом списания провайдера.

Вложенный Codex получает JSON Schema результата с отдельным полем `commitMessage`. Worker передаёт контекст карточки сам; лишние MCP из пользовательского окружения отключаются флагами только дочернего процесса. Для индексированного checkout сохраняется CodeGraph. Глобальный config.toml не изменяется. Поведение флагов описано в [официальной справке Codex](https://learn.chatgpt.com/docs/config-file/config-reference). Нестандартные настройки provider/profile и явные аргументы выбранного агента сохраняются.

## Проверка

Автотесты используют временные репозитории и синтетические задачи: реальные Git-конфликты, параллельные workspace, squash, восстановление, ограничения resolver, изоляцию окружения и Windows readonly junction-кеш. Платные модельные сессии и пользовательские задачи при этих проверках не запускаются. Успех этих тестов не доказывает семантическую корректность произвольного ответа LLM или совместимость linked-кеша с любым проектом.

Отдельная opt-in приёмка: `npx tsx scripts/smoke-sat3.ts models gpt-6-luna` запускает настоящие Codex-сессии в двух процессах worker, создаёт конфликт и обрывает процесс после публикации для проверки восстановления. Она расходует лимиты выбранного аккаунта. `npx tsx scripts/smoke-sat3.ts dependencies` выполняет настоящие параллельные сборки копии этого репозитория через общий кеш, затем проверяет отдельную установку после изменения lockfile. Обе команды сохраняют доказательства во временных каталогах; пользовательские задачи не ставятся в очередь.
